# Academic note author

Run from this repository. Read `docs/automation/README.md` for the commands and review schema, `docs/automation/writing-guide.md` for prose, and `docs/automation/repository-analysis.md` when changing rendering or components. Re-read the current `content/notes/newnote1.md` and relevant preceding section. Existing posts guide style and continuity; they do not replace original sources.

1. Inspect git status, current main and open task PRs. Reuse an appropriate review branch, or create a new branch from current main without moving unrelated work. Do not overwrite existing posts. A supplied baseline means comparison only.
2. Resolve the requested section in `.note-sources/catalog.json`. The first task needs the two PDFs and explicit PDF-page mappings; register those once when the user provides them. Inspect chapter headings to resolve ranges, including diagrams, footnotes and continuing equations. If uncertain, ask for the missing source/range and continue independent setup. Do not infer mathematical content from the section number, an existing post, or a paper.
3. `npm run notes -- prepare 5.10`, then `extract 5.10`. Open every selected PNG from both sources. Build the complete `review.json` item inventory: formulas, definitions, assumptions, examples and diagrams in source order. Transcribe ambiguities literally, mark them `unclear`, and place `[검토 필요: …]` beside affected manuscript material. Explain disagreements between sources; do not silently pick one. Complete the supported portions while clarification is pending.
4. Write `.note-work/5.10/note.md` for a first-year statistics student who knows calculus and basic probability. Preserve all source mathematics. Add only necessary definitions, connecting explanations and justified intermediate steps. Map each inventory item to an exact `noteExcerpt`; make a second source-to-draft pass for omissions. The validator can check coverage links, not semantic fidelity.
5. Decide visuals after prose. Research primary papers or original lecture material and record exact URL/figure/page and what was verified. Prefer original SVG or code using the source mathematics, with axes, scale, units, normalization and labels checked. Describe schematic limitations; never depict invented model results. Keep author-supplied existing artwork unchanged. Asset files go under the packet's `assets/` tree mirroring their future repository paths. Reused files need provenance and reuse permission.
6. Inspect `npm run notes -- inventory` before adding an interactive. Target 1–3 across the chapter, reuse existing ones where helpful, and do not add when the chapter already has more than three. For a new component, read the implementation guide in the repository analysis. Separate the computational kernel, test it against an independent calculation, then wire the real controls, lazy loading, resize messages and portable preview. The request already authorizes useful components; no routine extra approval is required.
7. Run `validate 5.10 --draft` during editing. When sources, equations and coverage are settled, run `preview 5.10` and `serve 5.10`. Inspect the full note at desktop and 390 px mobile widths, MathJax output, images, TOC, overflow, lazy iframe loading, keyboard controls, reset and boundary values. Record concrete evidence in `qa`; do not claim a browser check from a unit test. Run `fingerprint 5.10` after inspecting these exact bytes and store its output in `qa.fingerprint`. Recheck after edits.
8. For comparison, run `compare 5.9 --baseline content/notes/gm-ch05-59.md` then `preview 5.9`. Use the rubric in `docs/automation/pilot-5.9.md`; never assign quality scores without both sources. For new notes, `validate 5.10`, then `integrate 5.10`. Integration is exclusive-create and writes publishable content only on the review branch. Existing-note replacement needs a separately scoped user instruction, never a force flag.
9. Run `npm run check`, inspect the intended diff, commit and push only the review branch, and open a PR using connected GitHub tools (or authenticated `gh`). Include source coverage, ambiguities, figures, chapter budget, test results, browser evidence and any limitations. Preserve private PDFs/work packets. Inspect CI for the exact PR head and distinguish failures from existing baseline problems. Do not merge or deploy. If a write result is uncertain, read remote state before retrying.

Finish with the PR, what was verified, unresolved source questions and any needed input. “5.10절 작성” is an AI-agent workflow invocation, not a background schedule or a promise that the CLI itself calls an LLM.
